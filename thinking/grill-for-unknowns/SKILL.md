# 有据盘问：地图与领土（Grill for Unknowns）

## 概览

本技能的核心图景：

- **地图（Map）** = 你当前的认知：提示词、计划、假设、技能、文档摘录、agent 的心智模型。
- **领土（Territory）** = 客观现实：真实的代码库、产品约束、API、文档摘录、部署环境、用户品味、失败模式。
- **战争迷雾（Unknowns）** = 地图与领土之间尚未探明的差距。

盘问（Grill）在这里意味着：少数几个**有据可查的、实质性**的问题——不是无休止的审问；在非实质话题上不提问本身就是正确行为。目标是找到那少数几个**会实质改变计划**的答案（判据见"实质性问题"），并把逐步成形的共享理解写下来。

## 何时使用

- 用户说不要急着实现、要求更强的计划、或在编排实施工作之前想要一次严格的规划。
- 任务依赖不熟悉的文档、API、库、平台行为或源码约定。
- 用户有一个模糊的产品/设计欲望，很可能有**未知的已知**——他们看到结果就能判断好坏，但无法预先完整表述。
- 即将派发子代理或长跑编码 agent，需要一个更好的启动包。
- 之前尝试失败或卡住：因为做了假设、过度拟合通用最佳实践、或错过了真实的代码库约束。
- 审查计划 / spec / PR，需要在合并前压力测试隐藏假设。

**不要**用于：

- 琐碎、机械、验收标准已经明确的任务。
- 用户明确要求立即执行、且错误假设风险低。
- 一次工具调用就能直接验证正确答案、无需对话的任务。

## 操作模式

在未知数解决（或被显式接受为假设）之前，保持在**探索（Explore）或计划（Plan）模式**，不进入实施。

盘问有明确终点：**未知数台账清空时结束**——每个材料级未知数要么解决、要么给了默认值、要么被显式接受为假设。随着台账收缩，播报剩余数量（如"还剩 2 个材料级未知数"），让用户看见终点。

默认流程：

1. **复述地图**——总结用户的请求、预期产出、已知信息。
2. **读领土**——盘问前先查文档 / 源码 / 测试 / 配置；有文档或代码可查时，不要靠感觉。
3. **开一份盘问会话台账**——会话复杂到需要持久工作文档时使用（模板见文末）。
4. **建未知数台账**——按未知数分类法归类。
5. **建领域台账**——找出模糊术语、重载概念、词汇冲突、上下文边界。
6. **一次盘问一个决策**——按下文盘问流程。
7. **提议默认值**——低风险未知数选一个合理默认，标注为假设，不阻塞。
8. **持久化共享理解**——术语结晶时立即更新 `CONTEXT.md`；满足标准时才提议 ADR。
9. **创建或修订计划**——见"实施计划要求"。
10. **落地前请确认**——除非用户明确授权带标注假设继续，否则在共享理解确认前不落地计划。
11. **实施期间**——记录偏差和新发现的未知数。
12. **实施后**——产出讲解和测验 / 复查清单，让用户理解改了什么。

## 未知数分类法

| 类型 | 含义 | 如何暴露它 | 例子 |
|---|---|---|---|
| 已知的已知（Known knowns） | 需求已明确陈述，或被文档/源码证明 | 复述并引用 | "用 Stripe Connect；webhook 端点已存在。" |
| 已知的未知（Known unknowns） | 你/用户知道某个决策未定 | 问针对性问题，或选带标签的默认值 | "退款同步是单向还是双向？" |
| 未知的已知（Unknown knowns） | 用户看到能认出对错，但没说出口的标准 | 原型、草图、示例、参照 | "这仪表盘太企业味了，做得更操作员一点。" |
| 未知的未知（Unknown unknowns） | 谁都没考虑到的约束或可能 | 对文档/源码/测试/网络做盲区扫描；请教专家；搜先例 | "API 限流让这个同步架构不可能实现。" |

## 有据盘问流程

### 1. 先取证

问用户之前，先检查可用的 ground truth：

- 库 / 平台 / API 的官方文档。
- 本地源码、路由、模型、schema、迁移、测试、配置。
- 现有项目约定与相似实现。
- 错误日志、CI 失败、issue 评论、PR diff、之前的实施笔记。
- 用户指出的参考实现（即使是别的语言）。

缺失但可检索的文档去取；取不到就明说，并标记该主张未经证验。

### 2. 把证据转成压测问题

好的盘问问题同时具备三个性质：

- **实质性（Material）**——答案可能改变架构、范围、UX、数据模型、安全、权限或验收标准。
- **有据可查（Grounded）**——指向文档 / 源码行为或具体不确定性，不是泛泛的偏好钓鱼。
- **可作答（Answerable）**——用户能选选项、批准默认值、或提供参照。

坏问题：

- 胜任的 agent 本来就能默认的显性偏好。
- 任何研究之前的穷尽式问卷。
- 让用户回答代码 / 文档就能回答的问题。
- 让用户口头表述只能在看到时辨认的品味（"现代感对你意味着什么？"）——转到原型和参照。
- 没有上下文的开放式"还有别的吗？"。

### 3. 被阻塞时一次只问一个实质性问题

需要答案才能继续时：问一个问题，解释为什么重要，给推荐默认值。按决策树一个分支一个分支走，不要把整棵树一次倒给用户。

模板：

```md
阻塞问题：<问题>
为什么重要：<答案 A 还是 B 会改变什么>
证据：<文档 / 源码 / 测试 / 参照引用>
推荐答案：<默认值 + 理由>
如果你无所谓：我按 <默认值> 继续。
```

如果多个问题有用但不阻塞，留在盘问队列里，先问下一个未决的材料级决策。

#### 预算与退出规则

- 默认预算：每次会话约 **5 个阻塞问题**。超过时问用户是否继续。
- **泄压阀（Fatigue valve）**：如果用户回答变短或变得不耐烦（一字回复、"你定吧"），停止采访——把剩余未知数转成带标签的默认值，作为一批列出来供否决。
- 不再有阻塞问题时，不要继续一个个问：把残存的低风险未知数作为一条假设清单列出供否决。

## 领域建模：共享语言与 ADR

盘问同时要维护共享语言。发现模糊词或重载术语立即质疑，与 `CONTEXT.md`、代码标识符、文档、产品文案对照；术语结晶时**立即**更新 `CONTEXT.md`（只放术语表——不放计划、草稿或 ADR 内容）。

只有同时满足三条才提议 ADR：(1) 难以逆转；(2) 没有上下文会让人惊讶；(3) 是真实权衡的结果。否则记在会话 / 实施笔记里。

## 盲区扫描：发现未知的未知

当用户进入陌生领域、不熟悉的代码库部分、或高风险的集成时，跑一次盲区扫描：检索相关文档 / 源码 / 测试——包括载荷依赖的已知限制和失败模式——找出可能实质改变计划的未知的未知；用大白话解释；按实施风险排序；为每一条建议廉价解法。

```md
## 盲区扫描

### 最高风险的未知的未知

1. <未知数>
   - 为什么重要：
   - 证据：
   - 廉价解法：
   - 决策归属：用户 / agent / 文档 / 原型

### 大概安全的假设

- <假设> — 为什么安全，以后怎么验证

### 现在值得问的问题

1. <一个实质性问题>
```

## 未知的已知：头脑风暴、原型与参照

当用户只能从视觉或行为上认出正确答案、但无法完整表述时：

- 在接真实系统前先做廉价原型——比如单文件 mock + 假数据展示 3 个不同方向。
- 给出有意义差异的多个方向，而不是微小的变体。
- 请用户对示例、截图、演示、参考源做出反应——比如仓库内 2-3 个相似模块 + 一个外部参照，问匹配哪个行为。
- 把用户反应提炼为明确标准——当质量无法用测试检查时，把它们浓缩成一条简短评分标准，作为验证门。

## 实施计划要求

写计划时，把最可能改变的决策放在最前面：

1. **决策面**——数据模型、类型接口、权限、用户可见流程、API 语义、迁移策略。
2. **证据**——支撑计划的文档 / 源码引用。
3. **未解问题**——只有材料级的未知数，按风险排序。
4. **已决假设**——低风险默认值，除非纠正否则照用。
5. **原型 / 参照产物**——相关链接或路径。
6. **实施步骤**——小块、有序、带验证门。
7. **偏差策略**——领土与地图矛盾时，实施者该怎么做。

## 实施期间：笔记与偏差

复杂工作建一份临时实施笔记（如 `implementation-notes.md`），最小章节：计划快照、做的决策、偏差、新发现的未知数、验证。

默认偏差策略：

- 低风险且局部：选保守选项，记录，继续。
- 改变架构、数据迁移、安全、成本或用户可见行为：停下问。
- 文档与计划矛盾：信文档 / 源码，更新计划。

## 实施后：讲解、推销、测验

交付：

- 改了什么、为什么。
- 哪些未知数被解决、哪些假设仍在。
- 重要行为对应的文档 / 源码证据。
- 真实命令 / 测试的验证结果。
- 如果用户合并前需要理解：给短测验 / 检查清单——每条都能从报告本身回答。

## 子代理 / 编码代理启动包

派发子代理或外部编码 agent 前，准备启动包：目标、地图、先读哪些领土、四类未知数、偏差策略、验证门。

多子代理分工：

- **文档侦察兵（Docs scout）**——读官方文档 / 源码，返回约束。
- **代码库侦察兵（Codebase scout）**——映射现有模式与测试。
- **原型侦察兵（Prototype scout）**——做廉价的视觉 / API 替代方案，暴露未知的已知。
- **建造者（Implementer）**——计划稳定后才能动。
- **顾问（Reviewer）**——对照启动包与文档审查 diff。

## 校准：约束过紧 vs 约束过松

- **过紧（Over-constraining）**：agent 在转向更优时也照指令走。定义目标、约束、继续 / 停止规则；给实施判断留余地。
- **过松（Under-constraining）**：agent 默认泛泛的最佳实践，可能不适配产品 / 代码库。给参照、品味示例、验收标准。

## 验证清单

### 落地前

- [ ] 相关文档 / 源码 / 测试 / 配置已检查，或已声明无法访问。
- [ ] 已知的已知、已知的未知、未知的已知、疑似未知的未知都已列出。
- [ ] 阻塞问题是材料级的，且带推荐默认值。
- [ ] 低风险未知数转为带标签的假设，而不是阻塞进展。
- [ ] 计划以最可能变化的决策开头，而不是机械步骤。
- [ ] 长跑 / 子代理工作的偏差策略明确。
- [ ] 验证门在实施开始前已定义。

### 收尾前

- [ ] 偏差与新发现的未知数已记录。
- [ ] 测试 / 检查 / 手工验证实际运行并报告。
- [ ] 剩余假设可见。
- [ ] 用户 / 审查者拿到足以理解变更的讲解。

## 术语表（本技能固定用法）

| 中文 | 英文（仅首现锚定） | 定义 |
|---|---|---|
| 地图 | Map | 你对问题的认知模型：计划、假设、技能、文档摘录、agent 心智 |
| 领土 | Territory | 客观现实：真实代码库、API、测试、部署环境、用户品味 |
| 战争迷雾 | Unknowns | 地图与领土之间尚未探明的差距 |
| 已知的已知 | Known knowns | 已探明：需求明确或已被证据证明 |
| 已知的未知 | Known unknowns | 迷雾边缘：知道某个决策未定 |
| 未知的已知 | Unknown knowns | 探索过但变暗：用户看到能认、说不出口的标准 |
| 未知的未知 | Unknown unknowns | 深处迷雾：谁都没考虑过的约束 |
| 盘问 | Grill | 一轮一轮追问，直到共享理解 |
| 实质性问题 | Material question | 答案会改变架构 / 范围 / UX / 数据模型 / 安全 / 权限 / 验收标准的问题 |
| 压测问题 | Pressure-test question | 由证据转化、具备三性质（实质性 / 有据 / 可作答）的问题 |
| 阻塞问题 | Blocking question | 答案未得就无法继续的问题 |
| 决策树 | Design tree | 决策分支结构，一次走一个分支 |
| 泄压阀 | Fatigue valve | 用户答烦了就停止追问，残余未知数批量转默认值 |
