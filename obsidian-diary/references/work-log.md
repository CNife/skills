# 工作日志变体规则

## Vault 路径

- 根目录：`/mnt/c/Obsidian`（由配置文件 `~/.config/cnife-skills/obsidian-diary.json` 中的 `vaults.work.base` 决定）
- 日志目录：`工作日志/YYYY/MM/`（**注意：目录名用纯数字，不带中文**）
- 文件命名：`YYYY年M月D日星期X.md`（如 `2026年4月17日星期五.md`，**只有文件名含中文日期字符**）
- 模板文件：`工作日志/日志模板.md`

**⚠️ 常见错误**：不要将中文日期字符（`年`/`月`/`日`/`星期`）用在目录路径中。

| ❌ 错误 | ✅ 正确 |
|---------|--------|
| `工作日志/2026年/2026年5月21日星期四.md` | `工作日志/2026/05/2026年5月21日星期四.md` |
| `工作日志/2026年5月/2026年5月21日星期四.md` | `工作日志/2026/05/2026年5月21日星期四.md` |

完整路径示例：
```
/mnt/c/Obsidian/工作日志/2026/05/2026年5月21日星期四.md
                    ───┬─── ┬ ─┬─ ───────┬────────
                      项目  年 月    文件名（含中文日期）
```

## 模板内容

新日志文件从模板复制，模板仅包含一个 `# 待办事项` 标题和 tasks 查询块。

## 格式规则

### 标题结构

- `# 子系统名` → 一级标题，粒度到具体子系统（如 `# OneReason MCP` 而非 `# OneReason`）
- `## 具体任务` → 二级标题，按独立交付物拆分（两个功能 = 两条，框架搭建 ≠ 工具实现）

为什么按子系统拆分？**工作日志会被分享给团队或作为日报素材。** 同事和管理层按子系统定位感兴趣的部分，不关心子系统之间的混杂内容。粒度到子系统而非项目整体，方便不同角色快速扫读。

### 任务状态 Emoji

- ✅ 已完成
- 🔄 进行中
- 🐛 Bug修复
- 🔍 调研
- 🚀 已部署
- 🤝 会议/协作

### 内容规则

每个交付物 1-2 行。参考风格：简洁、只写结果、以子系统为维度。

**好的写法：**
- `✅ execute_cypher：只读查询 + 权限管控 + 结果序列化，经真实数据库验证`
- `✅ 单阶段 Dockerfile（256MB），MCP 端点响应符合预期`
- `✅ 确认 taplo-pre-commit 为 tamasfe/taplo 官方镜像仓库，非 fork`

**应避免的写法：**
- `❌ 完成 Wave 2-4：权限管控、序列化、工具实现`（用阶段标签代替了实际交付物，其他人看不懂"Wave 2-4"是什么）
- `❌ 4 轮最终验证全部 APPROVE，18 个测试用例全部通过`（验证过程不是交付物）
- `❌ 创建 .dockerignore：排除 .git/.venv/__pycache__/.env/tests 等 12 项`（配置细节在仓库里，不在日志里）
- `❌ 已提交并推送到 dev 分支`（Git 操作不是人的产出）
- `❌ 沉淀 5 条项目规则到 AGENTS.md`（AGENTS.md 是模型间通信协议，不是人的工作成果）
- `❌ Karpathy guidelines v2 清理`（纯模型内部标记，对人不产生信息量）

## 待办更新规则

1. **新增待办放到今天**：不修改历史日志中的待办列表，新任务记录在当天日志
2. **Obsidian 链接引用之前的待办**：用 `[[日期#标题]]` 格式链接到历史待办（文件名不带路径和 `.md`）
3. **之前的待办也要更新**：历史待办状态变化时，同步更新原日志中的 `[ ]` → `[x]`，并添加完成日期和链接

为什么同步更新原日志？**因为待办的状态变化本身就值得记录——回看时能看到"这件事是什么时候开始、何时完成的"。** 只在今日日记中更新而不改原日志，会丢失这个完整时间线。

文件开头固定为 `# 待办事项` + tasks 查询块，之后按子系统分组：

```tasks
not done
```
