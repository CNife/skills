# 领域建模附录

当盘问会话暴露出模糊术语、重载概念或持久的架构 / 产品决策时使用本附录。

## 仓库文件布局

大多数项目可用：

```txt
/
├── CONTEXT.md
├── docs/
│   └── adr/
│       ├── 0001-example-decision.md
│       └── 0002-another-decision.md
└── src/
```

多上下文项目可用：

```txt
/
├── CONTEXT-MAP.md
├── docs/adr/                 # 系统级决策
└── src/
    ├── ordering/
    │   ├── CONTEXT.md
    │   └── docs/adr/         # 上下文内的决策
    └── billing/
        ├── CONTEXT.md
        └── docs/adr/
```

惰性创建。没有值得记录的内容之前，不要添加 `CONTEXT.md` 或 ADR。

## CONTEXT.md 的职责

`CONTEXT.md` 是术语表 / 统一语言文件。它**不是**规格、草稿、实施笔记文件或 ADR。

用它记录领域 / 项目上下文特有的术语。

不要因为项目用了某个通用编程概念就收录它。

## CONTEXT.md 的写法

用 `../templates/CONTEXT.md` 作为骨架。

规则：

- 有主张：选一个规范术语。
- 定义要紧凑：一两句话。
- 定义该事物**是什么**，而不是它的实现细节。
- 同义词会造成混淆时，添加_避免_条目。
- 只有自然地聚合出分组时才用子标题分组。

## 盘问期间

立即质疑语言：

- "你说了 `account`；你指 `Customer`、`User` 还是 `Workspace`？在这个代码库里它们是不同的。"
- "代码用的是 `Project`，但计划里写的是 `Job`。`Job` 应该成为规范产品术语，还是计划改用 `Project`？"
- "你的术语表把 `Cancellation` 定义为取消整个订单，但新流程隐含部分取消。领域真相是哪个？"

术语结晶时立即更新 `CONTEXT.md`，而不是攒批次。

## ADR 规则

只有同时满足三条才提议 ADR：

1. **难以逆转**——以后修改有实际成本。
2. **没有上下文会让人惊讶**——未来读者会疑惑为什么选了这条路。
3. **真实权衡**——确实存在候选方案，且选择有影响。

显而易见的、可逆的或纯机械的决策跳过 ADR。

## ADR 格式

ADR 放在 `docs/adr/`，使用顺序编号：

```txt
docs/adr/0001-short-slug.md
docs/adr/0002-next-decision.md
```

用 `../templates/ADR.md` 作为骨架：短标题加 1–3 句话（上下文、决策、理由），状态 / 考虑过的选项 / 后果小节仅在它们有价值时使用。

## 什么值得写 ADR

- 架构形态。
- 上下文之间的集成模式。
- 有锁定效应的技术选型。
- 边界 / 范围决策。
- 刻意偏离明显路径的选择。
- 代码里看不出的约束。
- 非显而易见的被否决替代方案。
