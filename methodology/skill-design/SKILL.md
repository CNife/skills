# 技能设计

技能是一次可预测的行为改变。**agent 缺什么，决定技能类型；每类的重点，决定正文；三个通用问题，决定它能不能执行。**

用词拿不准时，以 [GLOSSARY.md](./GLOSSARY.md) 为准。

## 三类技能

| 类型 | agent 缺什么 | 重点 |
|---|---|---|
| **工具型** | 不知道工具的接口、状态和适用范围 | 心智模型和状态 |
| **流程型** | 执行顺序不稳、判断点不清 | 流程结构和完成标准 |
| **倾向型** | 默认行为不对 | 默认行为的覆盖 |

### 工具型

先写心智模型，再写命令：先回答它是什么、状态归谁，再写怎么调用。

- 心智模型回答「它是什么、不是什么」，用一个具体对象承载：池、队列、文件树都行，别停在抽象名词上。
- 状态要有归属：谁持有、谁在用、什么算空闲；存在不等于拥有。
- 失败态要写：什么时候无法确认安全，看到什么征兆。
- 适用范围要写：什么情况下用它，什么情况下换别的做法。
- 写坏的标志：只有命令清单，没有心智模型、状态和适用范围。

### 流程型

先判流程结构，再写步骤；先写顺序，再写判断点；先写完成标准，再写工具。

- 流程结构三选一，按「下一步是谁由什么决定」判：
  - **线性**：每一步按同一顺序执行，判断点只改变某一步的做法，不改变下一步是谁。写编号步骤。
  - **状态机**：下一步是谁取决于当前结果，流程要记住自己走到哪。写状态、转移条件、动作和失败态。
  - **DAG**：下一步要等不止一个前置完成才开始。写节点、依赖和汇合条件。
  - 命中多条时先找回环：回环跨越的整段按状态机写；其余部分按前置数量判线性或 DAG。
- 每个动作标出由谁执行：agent、脚本，还是人；判断留给 agent，固定动作交给脚本。
- 事实源写在对应步骤旁：状态和输入以什么为准。
- 人工确认点写明：哪些决定必须由人做，做完之后继续执行。
- 整份流程要有完成标准：实现者照着做完，不再问问题。
- 写坏的标志：把状态机或 DAG 写成编号步骤；步骤没有完成标准；判断写死进脚本，或固定动作留给 agent。

### 倾向型

先写默认行为，再写目标行为；先写适用范围，再写例外。

- 默认行为要具体：agent 现在下意识会怎么做，错在哪里。
- 目标行为要可观察：能指出 agent 具体做什么。
- 适用范围要写：哪些场景适用，哪些不适用。
- 自动触发的技能，触发词进 description：人会用什么说法点名这件事。
- 一条规则能覆盖的，就写一条；需要多条才说清时，用一组规则。
- 写坏的标志：价值观散文，没有可观察的目标；规则不改变行为。

## 三个通用问题

每个技能都要回答，顺序不限。没有对应内容的，明确答「无」。

1. **事实源是什么？** 状态、数据、规则以什么为准？它不可用时怎么办？
2. **脚本边界在哪？** 固定、脆弱、可重复的动作交给脚本；需要判断的留给 agent。
   - 脚本要自己处理错误，并给出可操作的提示。
   - 脚本里的数字给出判据或出处。
   - 先确认工具或依赖可用，再写命令。
3. **状态不符或进入失败态时怎么办？** 先确认当前状态和已有信息；把不确定的部分记录下来；退到更保守的做法；只写已经确认的内容。

## 写作规则

### 自动触发：description 决定 agent 能否发现

- description 写两件事：做什么，什么时候用。
- 用人会说的词；内部术语留在代码和参考文件里。
- 宁可稍微主动：agent 倾向于不用技能，而不是滥用技能。
- 上限 1024 字符；细节留在正文。
- 前半句说做什么，后半句说何时用；比如「当……时使用」。

### 上下文成本和认知成本

- 自动触发付上下文成本，手动触发付认知成本；两种成本和取舍判据见 [SKILL-MECHANICS.md](SKILL-MECHANICS.md)，决定用哪种前先读。
- 手动技能多到记不住时，读 [SKILL-MECHANICS.md](SKILL-MECHANICS.md) 的「路由技能」。

### 信息分层：正文写步骤，细节下沉到参考文件

- 每条路径都要用的，放正文；只有部分情况才用的，放参考文件，并在正文留指针写清什么时候去读。
- 参考文件保持一层深；超过 100 行，开头放目录。
- 正文控制在 500 行 / 5000 tokens 以内；超了先下沉到参考文件。要拆成新的自动技能时，判据见 [SKILL-MECHANICS.md](SKILL-MECHANICS.md)。
- 同一个概念的定义、规则、例外放在一起。

### 每一步都要有完成标准

- 完成标准要能判断「做完没有」。
- 标准要够狠：「每个调用点都核过」比「给出改动列表」更能逼出工作量。
- 标准模糊时，先把它写具体；完成与否只看当前标准。

### 用一个短词承载一块行为

- 找一个 agent 已经认识的词，一个概念只用一个词，反复用。
- 短词在正文里锚定行为，在 description 里锚定触发。
- 指路时直接写目标行为；禁令会把被禁行为拉进上下文。

### 给默认，再给例外

- 先给一个默认路径，再给例外；并列多个等价选项会让 agent 停在选择上。

### 例子只作对照

- 规则写判据，例子写一个具体技能的对应做法，标明出处。
- 例子集中在「示例」一节，不夹在规则之间。
- 例子过时不改规则；规则变了，例子跟着换。

### 剪枝：一个意思只留一处

- 同一件事只在一个地方写；其他地方指向它。
- 环境能查到的（目录结构、命令、配置），留在环境里；技能只写环境查不到的判断和例外。
- 逐句问：删掉这句，行为会变吗？不会就删整句。
- 写长期有效的信息；版本号、路径、人名这类会过期的东西，留在环境里。
- 技能会沉积：旧内容一层层留下。定期删旧，保持当前内容。

## 改造检查

1. **类型错**：用三类表重新判；重点和写法对不上，就是类型错。
2. **重点错**：重点埋在长流程里，读完不知道哪一段是必须的。
3. **通用问题缺**：三个通用问题有任何一个答不上来。
4. **臃肿**：用「信息分层」和「剪枝」过一遍。
